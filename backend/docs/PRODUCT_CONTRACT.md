# Product backend contract

Products use a shared model with CSV storage for fixtures and Neon storage online.

## Fields

| Field | Type | Requirement |
| --- | --- | --- |
| `id` | string | Required, nonempty; generated by `createProduct` |
| `name` | string | Required, nonempty |
| `price` | string | Required, nonempty |
| `q_available` | string | Required, nonempty |
| `desc` | string | Required, nonempty |
| `photos` | array | Required, nonempty |
| `tags` | string array | Optional; defaults to `[]` |
| `published` | boolean | Optional; defaults to `false` |

Required string fields reject missing, null, nonstring, empty, and whitespace-only values. Price and quantity remain strings. HTTP writes additionally require a nonnegative price with up to two decimal places and a nonnegative whole-number quantity.

`tags` contains any number of nonempty category strings. Missing or undefined defaults to `[]`; null, scalars, nonstring members, and blank members are rejected. Exact duplicates are removed while preserving order. Case and spacing in stored tags are preserved; the UI trims newly entered tags. Set `tags: []` to remove all categories. The old scalar `tag` field is no longer part of the product contract.

## Product operations

- `createProduct(data)` validates fields and generates a unique ID, replacing caller-supplied IDs.
- `getProducts()` and `getProduct(id)` return products, including `tags` and `published`.
- `getTags()` aggregates all product tag arrays into one sorted, unique list. Changes to products update this derived list automatically. A tag disappears when no product uses it.
- `editProduct(id, changes)` accepts partial edits. Omitted fields remain unchanged. A supplied `tags` array replaces the whole array. Unknown fields and changes to `id` are rejected.
- `deleteProduct(id)` removes a product. Missing IDs produce a not-found error.
- Failed validation must not persist partial changes.

## Storage and migration

`ProductDatabase` defines list, get, create, update, and delete. `CsvProductDatabase` atomically rewrites a temporary CSV file; arrays are JSON within CSV cells and `published` is JSON boolean text. Legacy CSV rows with scalar `tag` are read as a singleton `tags` array; empty or absent legacy tags become `[]`.

Neon stores `tags` as a nonnull JSONB array defaulting to `[]`. `neon/schema.sql` defines the table. `neon/migrate-product-tags.sql` preserves every existing nonblank scalar tag as a singleton array and drops the legacy column. The migration is idempotent and runs with schema setup and the updated batch function in one transaction via `npm run db:setup`.

Neon inserts, reads, and updates carry the array directly. Array changes are parameterized JSONB. Database credentials remain server-only. Public database roles have read access; only trusted backend credentials perform writes.

## Dashboard writes

Local creation uses a multipart form. `tags` is encoded as a JSON array string; omitted means `[]`. Images are optional: no upload produces the default `/assets/images/flower.svg` reference. Product data saves to Neon; uploaded image files persist in the local R2 emulator. Admin sessions are required for dashboard access and product mutations. Deployed image storage and enabling deployed writes remain pending.

Inline edits stage all field and image changes until Save changes. Undo restores loaded values. Local `PATCH /api/products` receives multipart `edits`, a JSON array of `{ before, changes }`, plus optional `photos:<product-id>` files. `before` is the full loaded product snapshot. Changes allow all editable fields. Existing photos may be kept or removed; new photos must be uploaded. Removing all photos restores the default.

`NeonProductDatabase.updateBatch` uses `neon/apply-product-edits.sql`: rows are locked in ID order and compared with the snapshots. A missing or changed row raises a conflict and rolls back the entire batch. New uploads are cleaned up on failure; previously stored images are retained. The SQL function uses caller privileges and is not executable by PUBLIC.

Local writes require a valid admin session, development mode, a loopback hostname, exact Origin, and the dashboard request header. Production writes remain disabled. Publication state persists; public menu integration remains deferred.

## Review hardening

Photo references must be an array of 1–10 strings, each at most 2048 characters. Each reference must be an HTTPS URL without embedded credentials, the bundled default image path, or a local `/api/images/<key>` path. Blank values, whitespace, backslashes, other schemes, arbitrary objects, and protocol-relative URLs are rejected. Upload byte limits and file signatures are also checked by the HTTP handlers.

CSV mutations acquire an atomic lock directory beside the canonical CSV path before reading. A competing writer fails with a busy error instead of overwriting another update; validation errors release the lock. This remains a local fixture adapter, not distributed storage. If a writer is forcibly terminated, remove its stale `.lock` directory only after confirming no writer remains active; locks are never automatically stolen. Neon is the deployed storage adapter.

The Worker's `authorizeAdmin` boundary checks the database session and current role before any product mutation, dashboard page/asset, or `/api/admin/*` request. Internal product functions are trusted server code, not unauthenticated HTTP endpoints. Creation and batch updates also use `authorizeProductWrite` to require the local-write flag, loopback host, exact Origin, and operation header. Deployed writes remain denied by this additional feature flag even for admins.

User authentication is documented separately in `ACCOUNT_CONTRACT.md`; enabling signed-in sessions does not enable deployed product writes.
